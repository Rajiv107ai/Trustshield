## 1. Assurance Level Classification System & Audit Principles

In accordance with strict audit safeguards:
1. **No Inflation of Evidence**: A local unit or integration test must never be labelled `[INDEPENDENTLY_VERIFIED]`. Independent verification requires an external, authorized third-party evaluator operating outside the developer custody boundary.
2. **No Conflation of Mocks with Deployments**: A client adapter verified against a local mock service must never be labelled `[DEPLOYED]` or `[INDEPENDENTLY_VERIFIED]`.
3. **No Conflation of Source Code with Built Images**: A Dockerfile and pinned dependency lockfile must never be labelled as a built, digest-verified OCI image.
4. **No Premature Authorization**: A protocol specification document must never be labelled `[FORMALLY_AUTHORIZED]` prior to genuine, signed executive governance board approval.

### Defined Assurance Tiers
- `[IMPLEMENTED]`: Specification, contract, or executable code exists in the repository.
- `[LOCALLY_TESTED]`: Verified by automated local unit, property, or adversarial pytest fixtures.
- `[INTEGRATION_TESTED]`: Verified across end-to-end multi-module pipeline execution.
- `[INDEPENDENTLY_VERIFIED]`: Cryptographic hashes, code boundaries, and protocol contracts independently verified by an external third-party auditor.
- `[DEPLOYED]`: Service, daemon, or image is actively running and authenticated in production infrastructure.
- `[FORMALLY_AUTHORIZED]`: Signed and sealed by the Executive Governance Board with genuine cryptographic signatures.
